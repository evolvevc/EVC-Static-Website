# Contact delivery

Build with Node 22+ and a public-only CONTACT_PUBLIC_JWK (base64 of an RSA-OAEP SHA-256 public JWK with an explicit kid). Supply the same value to the Function at runtime. Leaving it empty at build time selects the empty email draft. Set CONTACT_ORIGIN to the exact HTTPS site origin, CONTACT_FROM to an approved verified sender, and RESEND_API_KEY to a send-only runtime secret. The fixed recipient is contact@evolvevcap.com. Never put private keys in the project or host environment. The dedicated Contact configuration ignores the shared forms endpoint.

Run npm run build and node --test tests/contact-delivery.test.mjs locally. Tests use ephemeral in-memory keys and a loopback mail stub. Vercel route and firewall behavior require a separate hosting check before enabling. Verify POST /api/contact/ directly reaches the Function without redirects. Configure a blocking Vercel Firewall limit for that POST (initial suggestion: five requests per IP per ten minutes). Monitor send volumes and bounces. Browser timing and Origin checks cannot stop a direct client. An instance-local counter cannot enforce a global limit.

A 202 means Resend accepted an email request. Delivery, decryption and consent validation occur later. Unchanged retries in one page reuse the same envelope and provider idempotency key. Resend deduplication lasts 24 hours; page reloads, edits or later retries can duplicate messages. Assign a mailbox and bounce-monitoring owner. No durable queue or automatic recovery exists here.

On a restricted EVC workstation, save the JSON attachment in a protected directory and run node tools/contact/read-envelope.mjs <attachment-path> <private-PEM-path> <matching-base64-public-JWK-file>. Use an interactive, non-recorded terminal. The reader authenticates and validates before displaying visitor text. Avoid forwarding, session recording or leaving decrypted text in terminal history/scrollback. Restrict mailbox access with MFA. Define retention and deletion for attachments, mailbox, backups and provider copies. Generate and recover production keys under EVC custody outside this repository; retain retired keys offline while old messages need them. Coordinate site rebuild, Function key switch and cache expiry during rotation; old pages may need reloading. Never send private keys via email. No live delivery has been tested.

## Local Resend account test

Only the Windows loopback setup supports CONTACT_LOCAL_ACCOUNT_TEST=1. Set it in the temporary vercel dev process environment, with CONTACT_ORIGIN=http://127.0.0.1:3000 and CONTACT_FROM=onboarding@resend.dev. This selects the fixed Resend account mailbox evolvevc.2024@gmail.com. Leave the flag entirely unset for normal delivery to contact@evolvevcap.com. Never configure the flag in Vercel settings. Hosted Vercel runtimes cannot satisfy the Windows platform check; deployment markers, a mismatched origin or Host, or other flag values also reject the request.

Supply a send-only key through a masked PowerShell prompt only for an explicitly approved test. Bind vercel dev to 127.0.0.1:3000; use that exact address in the browser. Use one synthetic enquiry and the existing development public key. A 202 confirms provider acceptance. Verify receipt and offline decryption separately, then stop the server and clear the temporary environment.
For local work on Node 22+, set the public-only CONTACT_PUBLIC_JWK in the root ignored .env.local, along with CONTACT_ORIGIN=http://127.0.0.1:3000. Run npm run build and npm run dev:contact from the project root. The static build reads the public setting from .env.local if the process has no nonempty public-key setting. The launcher passes the local Contact settings to Vercel CLI, including its initial rebuild and Function process. An API key supplied through the launching process takes precedence over the file. Stop an older dev server before restarting. Reload /contact-us/ after rebuilding. A nonempty data-contact-key enables the POST branch in assets/js/forms.js.
## Readable email simulation (local tests only)

Run npm run build and npm test. The suite exercises CONTACT_DELIVERY_MODE=readable-local using two independent ephemeral RSA keypairs, an in-memory KMS unwrap adapter and a loopback Resend capture. No changes to .env.local are required. The ordinary Function has no KMS adapter. Only an explicitly injected adapter and test transport can exercise readable delivery. The simulation publishes a different key and processor notice. Existing attachment-key submissions keep their encrypted attachment, including during the simulated switch. Returning to the default rejects stale readable-key submissions; reload the form to obtain the active notice and key.

Do not enable this mode for real users. A live version requires approval for Vercel, Resend and Gmail to process readable fields; EVC-managed non-exportable KMS keys, workload identity, pinned key versions and rotation/revocation; verified sender, restricted mailbox, retention and deletion policies; reviewed rate limits, quotas, redacted monitoring, bounce ownership and rollback. Verify Function packaging of the CID logo, Gmail rendering, and delivery separately before release. Do not reuse the offline RSA key.
