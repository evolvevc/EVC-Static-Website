## Security and delivery semantics

An anonymous-reachable execute-as-owner web app is **publicly invocable**, regardless of whether its URL is shown to visitors. HMAC-SHA-256 in the POST envelope authenticates the backend before Drive, Mail, locks, or persistent writes. The signed bytes are UTF-8 `whitepaper-v1\n<timestamp milliseconds>\n<request UUID>\n<exact JSON body string>`. The timestamp must be within five minutes; comparison of fixed-length hex signatures processes every byte. The UUID is backend-generated. Replayed accepted IDs remain blocked for seven days, longer than the signature window. Do not add a GET send route or unauthenticated setup action.

The Vercel route allows POST JSON only, enforces a 4096-byte streamed body limit, exact production Origin and URL origin, same-origin fetch metadata when present, bounded fields, one email, explicit boolean consent, known resource IDs, and honeypot. Extra fields (file ID, URL, sender, override recipient, subject) are rejected. Apps Script validates again. Names/company control characters and HTML delimiters are rejected; HTML email values are escaped. Subject, admin mailbox and branding are server-controlled. MailApp sends as the executing owner; it does not set an arbitrary From address. The only visitor attachment is the selected approved PDF. The admin receives a separate plain-text request including server UTC time.

Origin and honeypot are not authentication: non-browser clients can forge Origin. Under the requested architecture, persistent caps bound email abuse but cannot verify ownership of the entered email or prevent anonymous quota-exhaustion denial of service. Apps Script itself can also be invoked enough to exhaust execution/service quotas before authentication finishes. If guaranteed availability, per-network enforcement, or verified recipient ownership is required, this is a blocker requiring an approved architecture/control change; no CAPTCHA, new datastore, or other infrastructure has been added.

LockService serializes reservation and sends. The persistent rolling 24-hour cap is 20 reservations, with three per recipient and a 24-hour recipient/resource cooldown. Remaining MailApp quota must cover both recipients. Failed PDF checks and uncertain sends retain their reservation; failures never refund capacity automatically. There are no automatic retries in the browser, Vercel or Apps Script. Replays and fresh request IDs for the same recipient/resource are blocked by the durable cooldown. The browser locks the submit button after success or uncertainty for that page session. A new deliberate attempt after cooldown is allowed; an uncertain request must be reconciled manually before doing so.

Each `WP_REQ_` property stores only timestamp, keyed recipient hash, resource ID, and separate admin/visitor states. Raw name, company and email are not stored in the ledger (they are processed transiently and included in their emails). Mailbox retention is controlled by the owner. Each send persists `unknown` before calling MailApp, then `submitted` only if MailApp returns. A throw/crash may leave `unknown` even when mail was sent, so never automatically resend it. A failed admin call does not prevent the independent visitor attempt; a persistent-storage failure stops further work. `submitted` is **not a delivery receipt**. HTTP 200 from Apps Script is not success: Vercel validates request ID and application state. Browser success requires visitor `submitted`; `unknown`, duplicates, limits, transport failures and malformed responses do not report delivery.

Cleanup runs under the same lock on authenticated valid requests, removing records older than seven days. Idle data remains until the next request; owner may remove expired `WP_REQ_` entries manually during decommissioning, without clearing recent reservations. At most 160 small records are allowed; full storage fails closed. The rolling cap normally bounds seven-day retention to about 140 records. Each record is well below 1 KB and the mapping is checked below 8 KB. Google documents 9 KB per property value and 500 KB total per property store; other properties in this already-created project share that quota. Never clear or overwrite unrelated properties. Quota/storage failures return generic uncertainty and do not trigger retries. Secret replacement would change recipient hashes: retain the same secret for this setup; any future rotation needs a planned pause of at least the cooldown plus signature window and retention of request IDs.
